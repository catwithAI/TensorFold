# 速度优化

本页介绍如何在 TensorFold 中开展速度优化：判断改动是否值得实现，找出内核受到哪种限制，在不拖垮机器的情况下分析性能，证明改动保持精确一致，并如实测量。本文不教授 CUDA；[延伸阅读](#延伸阅读)中的指南对此已有很好的介绍。

## 实现前先估算收益上限

编写内核或进行融合前，先算清楚它最多能带来多少收益。

- 使用 nsys 在真实服务上测量内核占解码步骤或提示词处理轮次的时间比例。
- 算出收益上限：假设改动完美实现，能消除多少时间。对带宽受限内核，这是它的耗时减去其字节量在设备带宽基准下的传输时间；对融合，这是被移除内核的耗时，加上被消除且原本完全暴露在关键路径上的读写耗时。
- 预先在服务层面设定门槛，而不是在内核层面设定：例如冷启动 TTFT 或解码步骤耗时的 3 %。测量前写下假设和预期范围。结果超出该范围时，首先排查测量。
- 停止规则：如果收益上限低于门槛，就不要实现。如果实现后的改动在服务层面的收益低于门槛，在[优化台账](optimization-ledger.md)中将其记为 `failed`，然后停止。

按收益大小而非改动成本给想法排序。在其他项目有效的想法也必须在这里重新估算：TensorFold 的内核和启动形状与报告该收益的项目不同。可以估算收益，但最终落地的实现必须基于我们自己的代码和模型自身定义，绝不能通过阅读或移植其他引擎的实现获得。

实例（GB10 上的 Qwen3.8-27B NVFP4，当时的 main，测量一小时，未写代码）：

- 将 SwiGLU 激活融合进 gate/up 提示词 GEMM，使输出在完成激活后只写一次。被消除的激活内核在 8k 时占冷启动 TTFT 的 3.38 %，32k 时占 3.11 %，带宽已达 246-248 GB/s。再加上同样可消除的 gate/up 写入，上限为 4.4 %（8k）和 4.1 %（32k），仅略高于 3 % 门槛。
- 将 GDN 解码扫描分散到更多 SM，让单个流的扫描使用更多 GPU 资源。TensorFold 的网格已经在 48 个 SM 上为每个流启动 768 个 block，该内核占单步耗时的 1-2 %。收益上限低于 1.5 %，因此未实现。

## 判断限制因素

只有在做过单一变量实验后，才能确定实际瓶颈。多数内核属于以下三种情况：

- **带宽。** 用传输字节量 ÷ 时间，与设备带宽基准比较（GB10 为 273 GB/s）。多数解码投影达到该值的 73-87 %。若内核远低于基准，且启动的 block 数少于 SM 数，则需要更高并行度：split-K、split-V 或 split-KV，同时固定合并顺序（见下文）。若低于基准但 block 充足，则是内核自身效率问题，例如加载、归约或输入布局。
- **启动及其他开销。** 单个内核仅耗时几微秒，但每步启动次数很多。应与相邻内核融合，而非继续调优该内核。
- **计算。** 大 M 的提示词 GEMM。可调整 tile、wave 和 L2 访问顺序（swizzle）。

### 逐内核审计

对真实服务做一次 nsys 捕获，即可得到回答整个步骤“时间花在哪里”的表格：

| 列 | 来源 |
|---|---|
| 内核、职责 | 内核名称，以及它处理的形状 |
| 每步耗时、占单步百分比 | 按步骤汇总的内核时间区间 |
| 每步启动次数 | 计数 |
| 网格、block 数与 SM 数的比较 | 启动记录 |
| 实际 GB/s | 根据检查点形状计算的字节量 ÷ 时间 |

标记所有占单步耗时超过 1 %，且 block 数少于 SM 数或带宽远低于基准的行。还要汇总每步读取的权重字节量：它能给出整个步骤的耗时下限，以及实际耗时距下限还有多远。上述例子的审计发现，没有占比超过 1 % 的内核少于 48 个 block；GDN out_proj 的带宽为 179 GB/s，而同一解码步骤中形状相同的 attention o_proj 达到 216。这比前面两个想法更值得追查。

## 安全地分析性能

- 在真实服务上使用 nsys。解码运行在 CUDA graph 中，因此使用 `--cuda-graph-trace=node`。每次服务启动只做一次捕获。GPU 忙碌时间是内核时间区间的并集，不是分析器汇总表中的数值。
- ncu 只用于合成的单内核测试，绝不能用于持有模型的进程。ncu 重放会将设备内存备份到同一内存池；在使用统一内存的 GB10 上，对完整模型运行 ncu 会耗尽内存并使机器挂起。
- 小内核：在模型内测量。孤立测量一个约 ~5 µs 的内核，测到的是启动开销和冷缓存。
- 内核微基准：轮换使用总大小超过 L2 的不同缓冲区，使权重来自内存，并说明方法。
- 实际运行了哪个内核，应以跟踪记录或日志为准，不能仅凭阅读分派代码判断。

## 精确一致性优先

改变 token 的加速改动不算速度优化。TensorFold 的规则如下：

- 每项速度改动，包括需要显式启用的改动，都必须保持贪心 token 哈希及设定种子的采样 token 与 main 一致。必须提供证据：在相同提示词上，对贪心和设定种子的采样分别与 main 比较 token 哈希。不允许有损权重或 KV 格式。
- 拆分（split-K、split-V、split-KV）必须按固定顺序合并部分和，且顺序不依赖网格或时序。不得对求和使用原子操作。
- 对每个无意改变的内核，在每个已构建架构上，逐函数比较 main 与分支的 SASS。将辅助函数移入共享头文件也可能改变 SASS；必须检查，不能仅凭推断。审查者需要可以重新运行的比较方式。
- 将新增和修改的内核注册到[内核契约](kernel-contract.md)。每个验收门槛都有必须失败的植入对照；如果对照通过，该次运行不能证明任何事情。

## 如实测量

- 按 A-B-B-A 顺序测试，每个测试组、每轮都启动新服务，并运行足够多轮，使每轮的收益方向一致。
- 每次启动服务前清空页缓存。
- 说明时钟状态（是否限频），记录 SM 时钟、温度和降频原因。出现降频或测试组之间 SM 时钟差超过 1 % 的轮次应丢弃。绝不要比较限频与不限频的结果。
- 对每个用于提供服务的二进制文件计算 md5，并写入结果。陈旧二进制文件的测量没有意义。
- 每张速度表都包含 token 哈希。使用推测解码时，速度取决于接受率，而接受率会随 1-ulp 的变化而变化：只在 token 完全相同的构建之间比较接受率与 tok/s，或分别报告每轮耗时和接受率。
- 在 1 和 4 个流下报告冷启动 TTFT 和普通解码，并在对应家族的形状上，与被替换的确切内核比较。即使位级一致，导致某个服务测试单元变慢的步骤也不会落地（#2620）；跨文件移动也必须对涉及的每个后端提供 main 与分支的速度比较，且不得退步（#2118）。
- 保存记录：每个发布数值对应的原始运行、服务日志和跟踪记录，存放在 `/tmp` 之外。

## 带宽受限机器上的无收益结果

GB10 的多数解码工作受带宽限制。计算侧改动（减少指令、改善 tile、增加重叠）在它上面可能测不到收益，但在独立显卡上仍可能有效。GB10 上的无收益结果不能为这类改动定论：可以附上 GB10 数据打开 PR，并请求在独立显卡上运行。

## 改动归属

- 先检查共享代码。跨家族部分位于 `zig/src/core/`，共享 CUDA 头文件位于 `zig/kernels/cuda/common/`；[优化台账](optimization-ledger.md)列出了辅助函数。已在一个家族上证明有效的改动应移植复用，不要重新发明。在 PR 中说明哪些部分属于 core，哪些仅属于后端。
- 在同一 PR 中更新优化台账对应行，包括将测得无收益的结果记为 `failed`。
- 性能配置开关的命名参见[配置档](profiles.md)，评估方法参见[评估](evaluating_cn.md)。
